本页定义传输层为承载 MCP 消息必须提供的能力、标准传输绑定，以及定义新绑定时需要满足的要求。

所有传输方式中的协议语义完全相同。传输方式是一种**绑定**：它定义消息如何分帧和传递、如何携带请求元数据，以及如何发出取消和终止信号。它不定义消息的含义：[消息模式](/specification/2026-07-28/basic/patterns)属于核心协议，在每种绑定中都相同。各绑定页面定义了以下标准传输方式：

1. [stdio](/specification/2026-07-28/basic/transports/stdio)：通过客户端启动的子进程的标准流，传递以换行符分隔的消息。
2. [Streamable HTTP](/specification/2026-07-28/basic/transports/streamable-http)：每条消息都通过 HTTP POST 发送到同一个 MCP 端点；响应以 JSON 对象或限定于该请求的 SSE 流返回。

客户端和服务器也可以实现[自定义传输方式](#custom-transports)。

## 消息

MCP 使用 JSON-RPC 编码消息。JSON-RPC 消息**必须**采用 UTF-8 编码。

绑定**必须**将客户端发送的 _请求_ 和 _通知_ 交付给服务器，将服务器发送的 _响应_ 和 _通知_ 交付给客户端。不存在其他消息方向：根据[消息模式](/specification/2026-07-28/basic/patterns)的规定，服务器不会主动发起 JSON-RPC 请求，客户端也不会发送 JSON-RPC 响应。

## 请求元数据

所有协议元数据都在消息体中传递：每个请求通过 [`_meta.io.modelcontextprotocol/*`](/specification/2026-07-28/basic/index#meta) 字段携带协议版本和客户端能力。

绑定**可以**额外将选定的消息体字段映射到信封元数据中。Streamable HTTP 传输将这些字段映射到 [HTTP 请求头](/specification/2026-07-28/basic/transports/streamable-http#request-metadata)，让中间组件无需解析消息体即可路由和检查请求。消息体仍是权威来源；进行元数据映射的绑定，会规定如何拒绝不一致的值。

## 取消

每种绑定都定义了客户端如何放弃正在执行的请求：stdio 中由客户端发送 `notifications/cancelled` 通知；Streamable HTTP 中则关闭该请求的响应流。协议层面的规则在所有传输方式中相同，详见[取消](/specification/2026-07-28/basic/patterns/cancellation)。

## 自定义传输方式

客户端与服务器**可以**实现其他自定义传输机制，以满足具体需求。协议与传输方式无关，可以在任何支持双向消息交换的通信通道上实现。

选择支持自定义传输方式的实现者，**必须**保留 JSON-RPC 消息格式、[消息模式](/specification/2026-07-28/basic/patterns)和逐请求元数据模型。自定义传输方式**应当**记录其连接建立、消息分帧和取消模式，便于实现互操作。

基于可靠双向字节流（如 Unix 域套接字或 TCP）的自定义传输方式，**应当**复用 [stdio 分帧方式](/specification/2026-07-28/basic/transports/stdio)，而不是另行定义：stdio 绑定本质上就是在字节流上传输以换行符分隔的 JSON-RPC，只有进程生命周期规则专属于标准流。

## 向后兼容

早期协议修订版通过 `initialize` 握手建立连接级会话，并允许服务器主动发起 JSON-RPC 请求。需要与这些修订版互操作的客户端和服务器，应按照[版本管理：向后兼容](/specification/2026-07-28/basic/versioning#backward-compatibility-with-initialization-based-versions)中的说明，检测对方所处的协议时代并执行回退；该节还提供了供实现者参考的兼容性矩阵。各绑定页面分别说明了对应传输方式的检测机制。

Model Context Protocol（MCP）为服务器向客户端发送结构化日志消息提供了标准方式。客户端通过 `_meta` 按请求控制日志详细程度，服务器则通过通知发送严重性级别、可选的 logger 名称，以及任意可序列化为 JSON 的数据。

## 用户交互模型

实现可以自由采用适合自身需求的界面形式来展示日志；协议本身不强制要求任何特定的用户交互模型。

## 能力

发送日志消息通知的服务器**必须**声明 `logging` 能力：

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

## 日志级别

协议采用 [RFC 5424](https://datatracker.ietf.org/doc/html/rfc5424#section-6.2.1) 规定的标准 syslog 严重性级别：

| 级别 | 说明 | 使用场景示例 |
| --------- | -------------------------------- | -------------------------- |
| debug | 详细的调试信息 | 函数入口／出口 |
| info | 一般性信息消息 | 操作进度更新 |
| notice | 正常但重要的事件 | 配置更改 |
| warning | 警告情况 | 使用已弃用功能 |
| error | 错误情况 | 操作失败 |
| critical | 严重情况 | 系统组件故障 |
| alert | 必须立即采取行动 | 检测到数据损坏 |
| emergency | 系统无法使用 | 系统完全故障 |

## 请求日志消息

### 逐请求的日志级别

要接收某个请求的日志消息，请在该请求的 `_meta` 中包含 `io.modelcontextprotocol/logLevel`。对于未包含此字段的请求，服务器**不得**发送 `notifications/message`。

存在该字段时，服务器**可以**在最终响应之前，通过该请求的响应流发送不低于所请求级别的 `notifications/message` 通知。`notifications/message` 的作用域限于请求：服务器**不得**通过 [`subscriptions/listen`](/specification/2026-07-28/basic/patterns/subscriptions) 流传递它，也不得通过设置日志级别的请求所对应响应流之外的任何流传递它。

## 协议消息

### 日志消息通知

服务器通过 `notifications/message` 通知发送日志消息：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/message",
  "params": {
    "level": "error",
    "logger": "database",
    "data": {
      "error": "Connection failed",
      "details": {
        "host": "localhost",
        "port": 5432
      }
    }
  }
}
```

## 错误处理

如果请求 `_meta` 携带的 `io.modelcontextprotocol/logLevel` 值不是已知的[日志级别](#log-levels)，服务器**应当**使用标准 JSON-RPC 错误拒绝该请求：

- 日志级别无效：`-32602`（Invalid params）
- 内部错误：`-32603`（Internal error）

## 实现注意事项

1. 服务器**应当**：
   - 对日志消息进行速率限制
   - 在数据字段中包含相关上下文
   - 使用一致的 logger 名称
   - 移除敏感信息

2. 客户端**可以**：
   - 在界面中展示日志消息
   - 实现日志过滤／搜索
   - 直观显示严重性级别
   - 持久化保存日志消息

## 安全

1. 日志消息**不得**包含：
   - 凭据或机密
   - 可识别个人身份的信息
   - 可能帮助攻击者的内部系统细节

2. 实现**应当**：
   - 对消息进行速率限制
   - 校验所有数据字段
   - 控制日志访问权限
   - 监控是否存在敏感内容
